# Native language boundaries

Hao's Cyna application lives in `src/` at the legacy feature paths. All 34 Cyna C ABI exports are declared in `src/hao_abi.cy`. Each export delegates to a public function in its feature module; those modules own the implementation. The executable imports the ABI module, and the static library uses it as its entry module. Public embedding declarations remain in `include/hao.h` and `include/addon.h`.

All project C sources and internal headers live under `src/bridge/`. Its Cyna import modules name the actual foreign surfaces: `qjs.cy` for QuickJS host calls, `transpiler.cy` for the Rust archive C ABI, `host.cy` for platform services, `uv.cy` for libuv, `jupyter.cy` for ZeroMQ, and `telemetry.cy` for native telemetry callbacks. Feature modules import these declarations and keep their behavior in Cyna. The legacy same stem modules `async/uv.cy`, `jupyter/zmq.cy`, `module.cy`, and `runtime_allocator.cy` remain normal Cyna callers of the bridge. The C declarations of Cyna exports used internally are in bridge headers, including `src/bridge/cyna_exports.h`. Headers exist for interfaces shared across C translation units, across C and Cyna, or with native consumer tests; private implementation details stay in their C sources.
The C boundary is limited to three kinds of work:

| Surface | Files | Why the C boundary remains |
| --- | --- | --- |
| QuickJS host integration | `bridge.c`, `module.c`, `errors.c`, `global/console.c`, `global/timer.c`, `js/addon.c`, `std/fs/native.c`, `std/process/native.c`, `std/http/native.c`, `std/http/server_uv.c`, `std/ffi/native.c`, `telemetry/interface.c`, `telemetry/metrics.c` | QuickJS values, callbacks, module loading, and runtime ownership cross its C API. Application policy is in Cyna and TypeScript feature modules. |
| Rust transpiler calls | `bridge.c`, `module.c` | These call the existing Rust archive through `libs/transpiler/include/hao_transpiler.h`. Rust owns TypeScript transformation. |
| Host and native APIs absent from Cyna std | `runtime_allocator.c`, `process_memory.c`, `std/process/execute.c`, `std/http/native.c`, `std/http/server_uv.c`, `std/ffi/native.c`, `jupyter/zmq.c` | The port needs shared allocation counters, macOS memory counters, bounded binary process capture and signal status, libcurl, libuv HTTP callbacks, libffi call layouts, and ZeroMQ frames with HMAC. The pinned Cyna std has `std.process.command().output()`, but its `Output` exposes text streams and exit code rather than Hao's bounded byte streams and signal result. No claim of language impossibility is made for these integrations. |

A source can appear in more than one row because one adapter crosses more than one native API. The current build compiles 17 project C sources. `src/bridge/jupyter/crypto.h` is shared by the native ZeroMQ adapter and its C consumer tests. `src/bridge/runtime_allocator.c` also supplies allocation statistics to telemetry and shares allocations with QuickJS and native libraries.

The allocator boundary has a concrete ownership reason. Zig's `runtime_allocator.zig` wraps its backing allocator and counts Hao-owned Zig allocations. In the Cyna port, the native adapters use `hao_alloc` and its accounting header; `runtime_allocator.cy` exposes that allocator to Cyna callers. QuickJS uses its own allocator and is reported separately. Moving only the counters into Cyna would split allocations from their corresponding frees and change the reported scope. This is a Hao runtime allocator contract, not evidence that Cyna std needs a new allocator API.

`errors.c` is a QuickJS callback adapter: it installs a `JS_NewCFunction` callback, reads the runtime's stack-trace setting from the QuickJS context, captures native frames with `backtrace`, and returns a QuickJS string. `errors.cy` owns the JavaScript `RuntimeError` definition and installation sequence. The native frame capture is platform work at the QuickJS boundary; no Cyna std expansion follows from this adapter alone.

Cyna owns HTTP URL and server limit policy (`std/http/native.cy`, `std/http/server_uv.cy`), FFI descriptor and decimal pointer policy (`std/ffi/native.cy`), metric policy (`telemetry/metrics.cy`), filesystem limits (`fs.cy`), package resolution (`package.cy`), notebook declaration rewriting (`jupyter/cell.cy`), runtime configuration (`config.cy`), and process result conversion (`std/process/native.cy`). `async/uv.cy` calls libuv loop entry points through `bridge/uv.cy`. The source inventory verifies that all legacy Zig paths have a Cyna or documented layout port and that C sources stay under `src/bridge/`; that inventory alone does not prove behavioral parity.

For Jupyter, `bridge/jupyter.cy` declares the raw ZeroMQ adapter ABI. `jupyter/zmq.cy` converts `Connection` and string values to and from that ABI, and `jupyter/wire.cy` exposes the wire handle and its operations to the kernel. The C adapter owns ZeroMQ sockets, multipart frames, and HMAC because the pinned Cyna std has no corresponding native APIs.
