# HTTP client and server

`std:http` provides buffered `request`, `get`, and `post`, plus a streaming
file sink for large GET responses:

```ts
import http from 'std:http'

const result = await http.download(
  'https://example.com/model.safetensors',
  '/tmp/model.safetensors',
  { maxBytes: 500 * 1024 * 1024 },
)
console.log(result.bytesWritten, result.sha256)
```

`download(url, path, options?)` runs network and file I/O on the existing native
HTTP worker. It copies decoded response bytes through a 64 KiB buffer, updates
SHA-256 as bytes are written, and never creates a JavaScript response-body
string or byte array. Network, transfer, and decompression buffers have sizes
independent of the downloaded file. Existing buffered APIs retain their behavior.

The destination's parent directory must exist. The download writes an atomic
file in that directory, syncs it, then replaces the destination only after the
body and HTTP framing complete successfully. A non-2xx status, exceeded limit,
truncated transfer, decompression failure, or file-write error rejects the
promise and removes the temporary file. Existing destination contents survive
such failures. Replacement is atomic, not a guarantee of directory durability
across a power failure.

Options:

- `headers` and `query`: same conventions as `get`.
- `maxBytes`: positive safe integer limiting decoded bytes; defaults to 1 GiB.
  The limit also applies when gzip or other supported HTTP compression expands
  a smaller wire payload.

The result includes `status`, `statusText`, `ok`, `headers`, final `url`, caller
`path`, `bytesWritten`, and lowercase `sha256`. It has no body accessors. SHA-256
covers the decoded file bytes and is not a publisher signature.

Downloads follow the existing HTTP client's maximum of three redirects.
This first streaming API is a file sink, not a JavaScript async iterable.
Progress callbacks, cancellation, timeouts, range/resume support, and general
streaming uploads remain future work. Compressed streams with trailing encoded
payload after the completed compression frame are rejected.

Run `hao test test/e2e/http` from the repository root for buffered request
regressions and streaming coverage: binary bodies, redirects, empty responses,
chunked/gzip framing, limits, truncated responses, and atomic cleanup. These
loopback fixtures use Python only as a test server; the runtime uses native I/O.

## Native server

`http.serve()` listens directly through Hao's libuv event loop. It does not use
Bun, Node, Python, or a subprocess. The same API is available inside Affon.

```ts
import http from 'std:http'

const server = http.serve({
  port: 8000,
  async handler(request) {
    if (request.method === 'POST' && request.url === '/echo') {
      return { json: request.json() }
    }
    return { body: 'Hello from Hao!\n' }
  },
})
console.log(`Listening on http://${server.hostname}:${server.port}`)
// server.close() stops accepting and closes active connections.
```

Run `hao examples/http-server.ts`, then `curl http://127.0.0.1:8000/`.
Use `port: 0` to choose an available port and read it from `server.port`.
The default bind address is `127.0.0.1`; `hostname` accepts a literal IPv4
address. The request exposes `method`, `url` (path plus query), lowercase
`headers`, and synchronous `text()`, `json()` and `bytes()` body helpers.
Return `{ status?, headers?, body? }` or `{ status?, headers?, json }`.
Bodies accept strings, Uint8Array and ArrayBuffer. Promise handlers are awaited;
throws/rejections and invalid responses produce a generic HTTP 500.

Defaults: 1 MiB request body, 16 MiB response body, 64 connections, and a
30-second connection deadline including handler time. Configure these with
`maxBodyBytes` (up to 16 MiB), `maxResponseBytes` (up to 64 MiB),
`maxConnections` (up to 1024), and `requestTimeoutMs` (up to one hour).
Request and response headers are limited to 16 KiB. Deadlines close the socket;
they do not cancel handler work. Synchronous compute blocks the JS event loop,
so deadlines cannot interrupt a synchronous model forward pass.

This first server buffers bounded bodies and closes each connection after one
response. It supports HTTP/1.0 and HTTP/1.1 requests, including Content-Length
uploads and HEAD. It does not yet provide TLS, keep-alive, chunked uploads,
streaming responses, WebSockets, or graceful draining. Response framing headers
are generated by the server. Duplicate or ambiguous framing headers are rejected.

`hao test test/e2e/http` includes native server/client round trips, asynchronous
handlers, raw malformed/fragmented requests, binary/UTF-8 data, limits, deadlines,
concurrency, and repeated close. Python is used only for raw-wire test requests.

Buffered `request`, `get`, and `post` also accept `maxBytes` (decoded response
limit, default 1 GiB) and `redirect: 'manual'` to return a redirect response
instead of following it. The default redirect policy follows up to three hops.
These client calls still lack native cancellation and request deadlines.
